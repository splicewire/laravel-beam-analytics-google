> You are in **splicewire/laravel-beam-analytics-google** — the Google Analytics child: a GA4 Data API TrafficSource for laravel-beam-analytics, install scope only.

A Laravel package (`Splicewire\Beam\AnalyticsGoogle\*`): a Composer Beam Extension. It contributes to a Beam host by
registering DOWN into manifests the host's beam already binds; a host requires it, and it appears.
Beam tier.

## What is here now

The scaffold `pnpm package:new` writes (splicewire-ecosystem): the service provider, `config/beam/analytics-google.php`
(merged under `beam.analytics-google.*`), one install step in beam's `beam.install.steps` (publishes
`beam-analytics-google-config`, order 900), and the Testbench and Pest harness.

Analytics-area ticket 14 added the child itself:

- **`Ga4TrafficSource`** (laravel-beam-analytics' `TrafficSource` port, key `google-analytics`): the install's GA4 property
  through `properties/{id}:runReport`, three reports per read (totals with the daily trend, top pages, top referrers).
  `covers()` is false for EVERY tenant scope, and it reads config only. `read()` runs only in analytics' refresh job.
- **`Ga4/`**: two narrow Saloon connectors (`GoogleTokenConnector` for `/token`, `Ga4DataConnector` for the Data API; conduit-fda's
  connector is the precedent), the service account's RS256 assertion (`ServiceAccountAssertion`, openssl, no Google SDK),
  `Ga4Config` (the NUMERIC property id, never a `G-` measurement id; the key file by path), and `Ga4ReadFailed`, whose messages
  carry a kind and a status and never a credential.
- **`Doctor/Ga4ConfigAudit`**: advisory, in beam's doctor manifest. It warns on a misconfigured child without quoting the key.
- **Wiring:** `WiresTrafficSource` (into `beam.analytics.sources` by `afterResolving`, by class-name string, idempotent) and
  `WiresDoctorAudit`.
- **Tests:** offline only. A Saloon `MockClient`, `preventStrayRequests`, a per-run generated key, provider URLs at a closed port.

What an extension usually adds next follows beam's particle doctrine
(`docs/agents/particle-doctrine.md` in splicewire/laravel-beam). The worked example of a resource, its nav
seat, its policy and a declared migration order is splicewire/beam-extension-demo; read its `AGENTS.md`
for the traps each one carries (columns that make a row visible, the seat-href split, the write axis that
fails closed without a policy).

## Rules that are easy to get backwards

- **Tiering.** This package requires `splicewire/laravel-beam` DOWN. It must never require
  `splicewire/laravel-beam-market` (an extension that dragged the marketplace in could not install on the
  bare Beam site it exists for), `splicewire/tower`, a `splicewire/laravel-satellite*` package or any
  `splicewire/laravel-tower-*`. The fences are declared in `composer.json` `extra.package-topology` and
  pinned by `tests/Topology/`.
- **Every registration is `bound()`-guarded.** Which manifests a host binds is a fact about the host; an
  extension that fatals on a missing optional manifest is worse than one that installs with one
  contribution fewer.
- **The provider never hand-lists steps.** A concern is a `Wires*` trait whose methods carry
  `#[Chained('register')]` or `#[Chained('boot')]` with a declared `order:`. `ScopesRegistrant` records
  this package as the registrant of every registry write in both phases.
- **Migration order is declared, not globbed.** When migrations land, `hasMigrations()` takes the stems in
  publish order and the install step gains `migrates: true` in the same commit.
- **Config.** A key lands in the same commit as the code that reads it.

## Vendored family-package conventions

Before editing through `vendor/` into another family package, read that package's own `AGENTS.md`.

## Testing

`composer test` (Pest on Testbench, booting beam with the providers its own harness lists). Install
through the local overlay: `composer.local.json` is generated by the ecosystem's `pnpm repos` and stays
gitignored.
